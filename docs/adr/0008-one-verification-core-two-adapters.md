# One schema-verification core, two adapters — not one function, not two forks

Two packages answer the same question — *does the emitted/compiled schema faithfully cover the bicep type graph, and vice versa?* — against two different representations of "the schema":

- **`generator/validate.go` (`ValidateEmittedSchema`)** runs inside the generation pipeline, immediately after `EmitSchema`, against the emitted Go **source string**. It extracts a set of quoted attribute names via regex (`attrNameInSource`) and diffs that set, both directions, against the bicep-derived expected path set (`CollectExpectedPaths`). It is **presence-only**: it cannot inspect an attribute's Terraform type, because the source has not been compiled. Its former doc comment claimed "Type mapping is correct (String↔string, …)" — that was false and is corrected.
- **`validate/validate.go` (`SchemaAgainstBicep`)** runs as a test/CLI check against the **compiled `schema.Schema`**. It walks the schema tree paired with the bicep tree, recursion driven by the concrete `schema.Attribute` type, and checks the type mapping (`validateType` / `isStringCompat` / `bicepDesc`) that the source adapter structurally cannot.

Both packages independently define the same `Mismatch` struct, the same `MismatchKind` enum + `String()`, near-identical `FormatMismatches`, and the same `joinPath`; both re-spell the same leaf rule (skip `SystemManaged` → `naming.CamelToSnake` → recurse into object / array-of-object / map-of-object).

**Decision.** Keep **both adapters** — they cross a real seam (two substrates: pre-compile source string vs post-init compiled schema), and each catches bugs the other cannot (the compiled adapter alone sees init/registration/type-mapping errors; the source adapter alone gates codegen before a file is written). De-duplicate only what is genuinely one concept: move the **model** (`Mismatch`, `MismatchKind`+`String`, `FormatMismatches`, `joinPath`) and the shared **leaf rule** (`AttrName(armName) → (snake, skip)` plus the recurse-into-kinds predicate) into `typegraph`. Both adapters consume that one core; neither redefines it.

We rejected a **unified visitor** (one traversal over the bicep graph, per-node handlers per adapter): the compiled adapter's walk is a *paired* schema×bicep traversal driven by the schema side, which will not fit a bicep-only visitor without leaking — the two traversals are genuinely different adapters, not one walk with two leaf handlers. We also rejected collapsing the two into **one function**: that would delete the pre-compile codegen gate or the post-compile type check, both of which are load-bearing.

**Consequence.** The shared comparison logic is unit-tested once against a hand-built `typegraph.Type`; each adapter is tested only for its extraction (source-string regex vs schema-tree walk). This lands naturally on top of ADR-0007 — `typegraph` is the home for "compare a schema representation against me." It does not reopen the Graduation gate (ADR-0006); the live-API verification harness keeps both checks, now sharing one model.
