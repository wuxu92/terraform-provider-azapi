# Separate the type-graph model from the code-emission engine

The `internal/native/generator` package fuses two responsibilities: the bicep-derived **type-graph model** (`Type`, `Property`, `PropertyFlag`, `TypeKind`, `ResourceDefinition`, `Envelope`, `ParseTypesJSON`, `PostProcess`, `ApplyAzwise`, and the model helpers `ARMTypeOf` / `FindProperty` / `IsolateArrayElement` / validator builders) and the **code-emission engine** (`EmitSchema`, `FileName`, `CheckFlagInvariants`, `ValidateEmittedSchema`). The runtime CRUD path (`resource/loader.go`, `resource/base.go`, `mapper/mapper.go`) imports `generator` but only ever touches the model — `Type`, `Property`, the `Kind*` constants, `ParseTypesJSON`, `PostProcess`. Naming the runtime's dependency `generator` misreads at every import site, and the model/engine fusion has a second cost: the stage ordering (`ParseTypesJSON → PostProcess → customizers.Apply → CheckFlagInvariants → EmitSchema → ValidateEmittedSchema`) has no single home, so it is re-spelled by hand at five call sites (`main.go`, `cmd/azapin-validate/main.go`, `resource/loader.go`, and two test files).

**Decision.** Extract the model into its own package, **`typegraph`**. `generator` keeps the emission engine and depends on `typegraph`; `customizers` depends only on `typegraph` (breaking the `customizers → generator` import cycle that forced the hand-orchestration). The runtime imports `typegraph` only. The ordered pipeline collapses to three named entry points, each naming a distinct graph and placed so the wrong one is unreachable at compile time:

- **`typegraph.BuildRuntimeGraph(data) → []*ResourceDefinition`** = parse + post-process, **no customizers**. This is the graph the runtime mapper reads; customizers are emit-only and must not appear here. `resource/loader.go` calls this.
- **`generator.BuildForGeneration(data) → []*ResourceDefinition`** = `BuildRuntimeGraph` + `customizers.Apply` — the graph as it was compiled into `_gen.go`. `cmd/azapin-validate` calls this before `SchemaAgainstBicep`.
- **`generator.Generate(data) → ([]GeneratedFile, error)`** = `BuildForGeneration` → per-def `CheckFlagInvariants` → `EmitSchema` → `ValidateEmittedSchema`, aggregating violations and mismatches into the error. `main.go` collapses to this one call.

We chose the full package extraction over merely adding a `Generate` entry point (which would fix ordering locality but leave the runtime importing a codegen-named package and the model/engine concepts fused). Because `azwise_overlay.go`/`ApplyAzwise` is called *inside* `PostProcess`, the azwise overlay travels with the model into `typegraph`, not with the engine — consistent with the Overlay glossary term (it augments the type graph).

**Consequence — the divergence becomes a compile-time impossibility.** Today `loader.go` correctly omits `customizers.Apply`, but only by discipline; a future edit could "fix" it and silently corrupt the runtime graph (the runtime mapper reads `Kind`/`Name`/`ElementType`/`Flags`/`Sensitive`, none of which customizers touch — so the omission is *required*, not accidental). After the split, the runtime cannot call `customizers.Apply`: it lives behind `generator`, which the runtime does not import. `BuildRuntimeGraph`'s name documents the invariant. This supersedes nothing in ADR-0002 — the runtime still resolves ARM names from the embedded type graph; only the package boundary moves.
